# 眼动意图输入与共享驾驶实施方案

日期：2026-10-14  
状态：软件与仿真部分已实现并完成自动验收，见 [实施记录](WHEELCHAIR_INTENT_SHARED_CONTROL_IMPLEMENTATION.md)；真人佩戴与人工标注可用性实验待完成。本文以下条目保留为原实施要求。

## 1. 目标与本次语义变更

将当前“稳定看左就持续左转、回正就前进”改成“眼动选择候选，确认后提交意图，下层持续完成有限任务”。解决自然扫视误改方向、用户必须频繁纠偏、延长停留后操作迟钝的问题。

用户掌握启动、停止和方向选择；下层负责运动执行、朝向修正、通道居中、门前对正和允许范围内的避障。避障系统只能在已确认意图内行动，不能从“空间安全”推断“用户想去那里”。

本方案替代旧方案中的连续眼动遥杆映射，但保留旧模式用于对照。相关资料：

- [原共享控制方案](EYE_WHEELCHAIR_SHARED_CONTROL.md)
- [当前避障概述](WHEELCHAIR_OBSTACLE_AVOIDANCE_OVERVIEW.md)
- [窄道改进方案](WHEELCHAIR_NARROW_PASSAGE_IMPROVEMENT_PLAN.md)

本轮只实施软件与仿真，不自动连接实机发运动命令，不修改 ESP32 固件。

## 2. 当前实现及需改变之处

已检查 `wheelchair_shared_ws/src/eye_shared_control/eye_shared_control/core.py`、`config/eye.yaml`、共享消息及 `wheelchair_control/passage.py`。

- 当前 EyeMachine 通过 250 ms 停留和方向阈值，将视线直接变成 FORWARD/LEFT/RIGHT。
- 当前第一次双眨眼启用会话；PAUSED 状态另有单眨眼恢复手势 `ResumeGesture`，恢复时输出 FORWARD。
- 当前闭眼开始会清除方向候选。新模式确认需要保留闭眼前选定的候选，因此不能直接套用此逻辑。
- 当前共享 ControlIntent 是动作式意图，包含 command、enabled、valid、ttl 等字段，不能直接表达一次已确认任务和候选选择。
- 下层已有 corridor_assist 和 passage 模块，应复用并验证，而不是假定通道辅助仍未实现。
- 眼动目前只有水平信号及睁闭眼状态，不能确定用户看中了哪个现实物体。候选必须显式呈现，不能宣称实现三维注视选门。

单纯缩短 dwell 会增加误触发；延长 dwell 会增加迟钝。新模式通过“候选即时反馈、确认后执行”分别处理反馈速度和运动授权。

## 3. 第一版明确的交互规则

模式名建议 `interaction_mode:=intent_confirm`；旧模式保留为 `gaze_joystick`。模式通过启动配置选择，运行中切换必须先停稳并清除授权。

### 候选选择

| 眼动 | 候选含义 | 未确认时 |
|---|---|---|
| 正中 | 继续当前前进方向/当前唯一通道 | 不改变活动任务 |
| 看左 | 向左调整朝向 | 不改变活动任务 |
| 看右 | 向右调整朝向 | 不改变活动任务 |

原始方向可立即用于预览；方向稳定经过 dwell 后候选才可确认。初期保留 250 ms、进入阈值 0.25、退出阈值 0.15 作为可配置实验初值，不承诺是最优参数。

左右候选第一版明确显示“左转/右转一个有限角度”，而不是“选择左侧物体”。转角参数可从 15°仿真实验开始，但必须落在执行器已验证的可实现动作范围内。路口分支选择属于后续扩展。

### 确认与停止

- 双眨眼确认当前稳定且有效的候选；停止状态和运行状态使用同一种提交语义。
- 第一次闭眼开始时冻结候选 ID、内容、候选版本和有效期，随后眨眼中的水平波动不改变它。
- 第一次短眨眼结束后，仅在配置的双眨眼间隔内等待第二次；超时、长闭眼或无效源使确认事务失效。
- 确认期间可继续显示其他预览，但提交对象只能是冻结候选。若候选撤回、上下文版本改变或用户重新稳定选择其他候选，应取消本次确认，不悄悄替换对象。
- 无稳定候选时双眨眼不启动；不得默认确认前进。
- 一次确认只产生一个意图事件。确认后消耗候选并重置眨眼计数；新候选需重新建立，不沿用残留眨眼。
- 长闭眼沿用约 650 ms 初值，触发 STOP/CANCEL，不经过方向 dwell；停止检测阈值本身仍造成延迟，必须测量，不称为瞬时急停。
- 单眨眼不启动、不恢复。`intent_confirm` 模式禁用旧 `ResumeGesture` 的单眨眼恢复逻辑；旧模式可保留。
- 回正只选择候选，不自动前进；持续侧视不无限旋转。
- 正常短眨眼和健康自然扫视不改变已确认任务；检测 invalid 或源超时仍立即撤销任务授权。

双眨眼也可能自然发生，因此它是待验证的确认方案，不是可靠性保证。验收必须覆盖自然眨眼、阅读和观察场景。若误提交不可接受，优先引入可用的独立确认开关/其他明确手势，而不是宣称仅靠水平位置已能识别人类意图。

## 4. 第一版任务定义和完成条件

### CONTINUE：继续当前方向或唯一通道

- 确认时锁定参考方向、通道对象（若有）和任务范围。
- 在清晰直走廊中由下层居中；门洞场景复用门前对正/过门辅助。
- 开阔区域保持确认时方向，只做授权范围内的局部修正，不自行选择远处目标或新通道。
- 到达通道末端、门洞出口、分叉决策区、范围上限或无法安全执行时结束/阻挡并停车。
- 第一版增加任务最大时间和最大累计路程；建议仿真初值 10 s、3 m，任一到期即停车。用户再次确认可建立新任务；不能由眼动帧或心跳自动续长任务范围。
- 时间和路程按实际反馈累计，切换子动作或重规划不能清零。以上数值是试验初值，实机需另行评估。

### ADJUST_HEADING：有限朝向调整

- 参数为有符号相对目标角；接收后先停止旧运动、确认停稳，再锁定相对停稳姿态的绝对目标朝向。
- 左右选择分别对应正/负转角，采用实际 odom 和提前制动跟踪目标。
- 达到目标并停稳后任务完成，保持 STOP，不自动接前进。
- 转动包络不安全则拒绝/阻挡，不能反向旋转或前进代替。

### CANCEL

- 立即撤销活动任务和所有尚未执行的候选，发 STOP；不需要已启用或健康的方向候选。
- 长闭眼、用户停止、健康故障和任务管理器超时均进入取消/停车路径。
- STOP 后不保存可被单眨眼或旧消息自动恢复的任务。

### 后续扩展，不属于第一版必交范围

识别路口分支后，提供具体 branch_id 的候选让人确认。进入分支需验证转入轨迹，歧义时停车。不能把当前 corridor_assist 自动扩展成未经确认的 90°转弯导航。

## 5. 系统模块与职责

```text
眼动检测 / 源有效性
    ↓
候选选择与确认状态机
    ↓ 一次性意图事件       ↓ 健康心跳 / CANCEL
意图任务管理器 ← 下层健康与任务执行反馈
    ↓ 当前有限任务、任务 ID、授权范围
共享驾驶：通道/门洞辅助、有限转向、离散动作规划
    ↓
最终安全检查 → 固定档位执行器 → 仿真底盘
```

底层实际动作仍只有 STOP/FORWARD/LEFT/RIGHT。任务层可以持续存在，但动作层必须保持短期有效、持续检查和独立失效停车。任务管理器或规划器崩溃不得使执行器继续依赖最后一个长期任务。

输入来源显式选择，同一时刻只有一个任务事件生产者。眼动与键盘使用相同任务接口、授权和安全链路；禁止多个节点同时向底层旧 ControlIntent 话题写入互相竞争的命令。

## 6. ROS 接口修改要求

由任务/规划 agent 维护 `wheelchair_interfaces`，先提交接口定义并与眼动 agent 对齐。以下是字段语义，具体 msg 命名可以调整，但必须版本化并写入 README。

### CandidateStatus：候选与反馈

包含候选 ID、候选版本、类型、参数、稳定/可确认标志、失效时间、提示文本、上下文 ID/版本。候选版本只在语义或上下文发生实质变化时递增；心跳和普通地图刷新不能无条件撤销所有候选。

第一版候选由眼动侧按固定三方向语义生成；下层提供可用性和上下文反馈。不能把“可确认”显示成“承诺可执行”，最终必须重新检查安全。

### IntentEvent：确认或取消事件

建议字段：`header`、`source_session_id`、`event_id`、`kind`（CONTINUE/ADJUST_HEADING/CANCEL）、`candidate_id`、`candidate_version`、`context_id/version`、`relative_yaw`、`ttl_ms`。

- 接收方依据 session/event_id 去重，同一事件重发不得再次转向或重置任务预算。
- 新 session、过期、乱序和撤回候选不能启动动作；session 切换时先取消旧任务。
- 确认有 ACK（接受/拒绝及原因）。发送方可以有界重试同一事件，不能生成新 event_id 伪装成重试。
- ACCEPTED 只表示接收授权，不表示车轮已经动作；RUNNING、STOPPING、COMPLETED 等由执行反馈决定。

### InputHealth：源健康心跳

包含 header、source_session_id、sequence、source_valid、源样本时间或可用年龄、ttl。健康心跳只维持输入可用性，不新建/恢复任务，也不刷新任务时间和路程预算。

不能用定时重发让旧检测结果变新。现有 Float32MultiArray 没有采集时间戳，过渡阶段明确只能按接收时间检测陈旧数据；优先增加带源时间和序号的眼动消息，并保留旧输入适配器。

### TaskStatus：任务执行状态

包含 task_id、关联事件 ID、状态（IDLE/ACCEPTED/RUNNING/STOPPING/COMPLETED/BLOCKED/FAULT）、目标/参考、剩余预算、实际子动作、原因、是否可接受新确认及候选上下文版本。

### 兼容性与安全语义

- 可以保留旧 ControlIntent 作为任务管理器到现有规划器的适配输入，但不能只做名字转换：有限角度任务必须能完成，通道任务参考不得每周期重置。
- 原 `/wheelchair/action_safe` 及执行器看门狗继续存在；如扩展动作元数据，需同步预测器和执行器。
- 停车恢复沿用“禁用 STOP → 停稳/健康检查 → ready → 新确认”，由任务管理器协调，用户不需要额外重复眨眼两次完成内部握手。
- CANCEL、健康无效/超时与故障优先于提交事件。一个确认事务内若发生失效或取消，该事务不能在恢复后生效。
- 指令采用 volatile、小队列；不得用持久化历史消息让重启后的消费者恢复运动。
- 单调时钟负责看门狗；消息时间用于陈旧检查，明确真实眼动与仿真 /clock 的适配方式。时钟回跳、暂停恢复和重启使旧授权失效。

## 7. 任务管理器状态与替换规则

1. 启动为 IDLE/STOP，不凭“眼动健康”自动启动。
2. 收到有效确认，检查候选、上下文、输入健康和下层 ready，建立任务 ID 和预算。
3. 新确认替换旧任务时，先取消旧任务并 STOP，停稳后重新校验新候选和预算，再启动新任务。只保留最多一个最新待处理确认，不排长队。
4. 待启动事件在等待停稳期间过期，必须拒绝并提示重新确认，不能静默延长 TTL。
5. 活动任务持续运行不需要重复确认；但必须有新鲜的源健康、下层状态与动作检查。
6. 正常扫视只更新候选，不更改 task_id、目标、通道参考或辅助阶段。
7. 完成、阻挡、取消、超时和故障后保持 STOP；需要新确认建立后续任务，不自动恢复。

源失效与“意图分类不确定”必须分开：健康但意图不明确时不提交新任务；真实输入链路失效时撤销正在运行的任务。

## 8. 下层规划改造

### 复用部分

复用现有 corridor_assist、passage 检测、微转向能力、固定档位模型、完整轮廓与制动检查。读取当前测试与实现确认能力边界，不依据旧文档重复实现已完成部分。

### 必改行为

- 下层以 task_id 和锁定参考运行，眼动候选改变不触发 planner.cancel。
- 居中/对正应在直行尚安全时提前进行，不仅在 BLOCKED_FORWARD 后才介入。
- 允许在同一已授权通道内多次有限微调；硬安全约束、方向权限和任务预算持续有效。
- 通道结束、识别歧义、分叉和超过范围时停车，不自动选择下一条路线。
- ADJUST_HEADING 使用角度闭环及制动预测，不能用一直发 LEFT/RIGHT 来代替任务完成逻辑。
- CONTINUE 任务在开阔区域不能任意附着到侧面新识别通道；任务上下文变化须有方向一致性和明确范围规则。
- 用户取消优先于所有保持、侧向滞回和规划序列。预测搜索超时不能无限续发上一次非零动作。

## 9. 用户反馈和延迟测量

至少显示：当前任务、当前动作、候选方向、候选是否稳定、确认已接受/拒绝、正在停车/执行、任务完成与阻挡原因。

分开记录以下时间，避免把机械停稳等待误认为眼动识别迟钝：

1. 采集/接收到候选预览。
2. 稳定候选建立到确认完成。
3. 确认完成到 ACK。
4. ACK 到实际开始运动，单独标记停车转换时间。
5. 停止手势起始、停止识别、STOP 发布和实际停稳。

P50/P95 和最坏观测值分别记录。没有采集时间戳时，不把接收后延迟标成相机端到端延迟。第一版不为了减少数值而删除制动等待或放宽失效超时。

## 10. Agent 分工与实施顺序

### Agent A：眼动候选与确认

- 修改 eye_shared_control/core.py、node.py 和 eye.yaml，增加 intent_confirm 模式。
- 实现候选冻结/版本、双眨眼事务、CANCEL、健康输出与反馈。
- 禁用新模式的单眨眼恢复及回正自动前进。
- 保留检测、标定和旧模式，提供合成眼动测试与新模式启动说明。

### Agent B：共享接口、任务管理与规划接入

- 先维护共享 msg 和话题约定，并提供模拟 IntentEvent 发布工具。
- 新建可单元测试的任务管理器及 ROS 包装；实现去重、ACK、替换、预算和恢复握手。
- 接入已有规划器，完成 CONTINUE 和有限 ADJUST_HEADING。
- 验证有限任务与短期动作授权不混淆，保留独立停车链路。

### 联调负责人

- 冻结接口后双方并行实现；只有接口所有者改共享消息，避免冲突。
- 顺序：任务事件脚本 → 仿真任务闭环 → 合成眼动 → 真实摄像头控制仿真。
- 默认硬件关闭；完成验收后再考虑实机迁移。
- 本文提供任务分工，不表示已经启动任何 agent。

## 11. 必须通过的验收

### 眼动单元测试

- 未确认时，无论看左、右、正中多久都不能新建运动任务。
- 有活动任务时，健康扫视不改变任务；回正不自动前进。
- 单眨眼不启动/恢复；双眨眼只确认冻结且仍有效的候选。
- 眨眼中的瞳孔扰动、第三次眨眼、重复消息和超时不能多次提交。
- 无候选、候选撤回、过期、版本改变时拒绝确认。
- 长闭眼、invalid、超时取消任务；恢复后没有新确认就不能动作。

### 任务与规划集成测试

- 确认一次 CONTINUE，在任务范围内持续居中，不要求一直看正中。
- 确认一次有限转向，只执行一次，达到目标并停稳后不自动前进。
- 替换任务先停稳；旧 ACK、旧事件重试、重启、session 改变不能恢复旧任务。
- 时间/路程预算不因重规划、重复确认事件、心跳或子动作切换清零。
- 在过门、微调和阻挡等每个阶段取消，都停止并清除后续段。
- 分叉不自动选路，超出边界或无安全轨迹时给出原因。
- 源、管理器、规划器和执行器分别中断时，最终均按各自看门狗失效停车。

### 可用性实验

对比旧 gaze_joystick 与新 intent_confirm。记录自然扫视、阅读标识、观察路人、正常眨眼和明确控制动作；必须有人为标注的真实意图，不能以算法自己的输出作真值。

指标：每分钟误提交次数、漏确认率、确认时间、每段路的用户操作次数、任务完成率、停止延迟、碰撞/最小间距和主观操作负担。方向分类准确率不能代替误提交评估。

验收报告需同时提供任务成功和正确拒绝的案例。不能仅用“未移动所以无碰撞”证明系统好用，也不能以仿真通过宣称实机安全。

## 12. 交付与禁止事项

交付代码、接口说明、参数语义、旧/新模式启动命令、自动化测试和可复现仿真记录。更新项目现状文档时只描述已验证行为。

禁止：默认引入大模型/深度意图网络代替明确交互；没有标注数据就宣称能识别观察与控制意图；把健康心跳当永久运动授权；取消超时或通过无限延长 TTL 掩盖延迟；绕过安全链路；修改检测/标定核心以完成不相关重构。

如果规则确认方案的误触发仍不能满足需求，再收集真实时序数据评估意图分类器或独立确认输入。分类器只能提供候选证据，不能默认绕过显式启动、停止和硬安全约束。
